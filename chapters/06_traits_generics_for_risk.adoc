== Add a pre-trade risk check the type system enforces

<<ch-error-design-under-corruption,Error design under corruption>> made error outcomes explicit under corrupted input. You now know where replay fails and why. This chapter moves one step earlier in the flow and asks a stricter question: should this order be allowed to mutate state at all?

That decision belongs at a hard boundary. If every caller can invent risk behavior ad hoc, policy drifts and incident review becomes argument instead of analysis. You want a single contract that every check follows, plus an execution model you can tune for either static performance or runtime flexibility.

Traits and generics give you that boundary. Traits define behavior. Generics determine when concrete behavior is bound.

=== Risk checks are preconditions, not reports

Treat risk checks as preconditions, not analytics. If the check fails, state must remain unchanged.

Common examples are enough for this chapter:

1. Position cap: total shares cannot cross threshold.
2. Notional cap: order value cannot cross threshold.
3. Rate cap: order flow cannot exceed limit per interval.

The finance details are secondary. The systems property is primary: validation happens before state mutation.

Run this chapter's tests first to see both paths:

[source,shell]
----
cargo test --test integration_ch06
----

[WARNING]
====
*Risk boundaries are a business decision coded into types.* Once the trait is public, changing risk checks becomes a semver-breaking change. That is the feature, not a bug. Good risk architecture makes bypass expensive.
====

=== Traits model behavior without inheritance

Define one contract and force all implementations through it.

.The RiskCheck trait: a contract for pre-trade validation
[source,rust]
----
include::../src/ch06/risk.rs[tag=risk_check_trait]
----

This trait is intentionally narrow: input state, candidate order, deterministic decision. A narrow trait does three useful things:

1. Keeps implementations comparable.
2. Keeps tests simple.
3. Keeps accidental side effects out of validation.

If you later add a new rule, the compiler enforces trait conformance immediately. That avoids partial migrations where some code paths enforce new limits and others still run old logic.

Your first concrete check should reject a position-cap violation with the dedicated variant. Avoid stringly-typed rejection reasons here. Structured variants make both tests and operations reliable.

As soon as a second rule exists, avoid ad hoc chaining in callers. Keep composition inside the risk layer so ordering and short-circuit behavior are consistent across all entry points.

=== Compose multiple checks without losing determinism

Most deployments need more than one rule. The important design choice is not just which checks exist, but how they compose:

1. Fixed order, stop at first violation.
2. Fixed order, collect all violations.

For low-latency paths, stop-at-first-violation is often the practical default because it bounds work and keeps rejection behavior predictable. For offline diagnostics, collect-all can be useful. Pick one behavior for each engine mode and document it.

Determinism matters more than richness. If rule order changes between runs, operators cannot compare outcomes reliably.

=== Generics and monomorphization in hot code

Use generics when the engine can bind to one known risk-check type at compile time.

.Monomorphic engine: generic type parameter resolved at compile time
[source,rust]
----
include::../src/ch06/risk.rs[tag=generic_risk_engine]
----

Rust monomorphizes generic code. For each concrete `T`, the compiler emits a specialized version. That produces direct calls and often better inlining in hot paths.

Tradeoff summary:

1. Runtime: fast, no vtable dispatch.
2. Build/binary: more code generated per concrete type.
3. Deployment: stable when risk set is mostly static.

Anchor this with two tests: one acceptance case and one explicit violation case. If both pass, your generic path is enforcing boundary semantics correctly.

When you add multiple rule types, extend tests to verify composition order. Example: if both notional and position limits would fail, assert which violation is returned first.

[NOTE]
====
*Monomorphization is the default for generics in Rust.* You get compile-time code generation "for free" (the cost is build time and binary size, not runtime). You only pay for dynamic dispatch if you explicitly use trait objects.
====

=== Dynamic dispatch when flexibility matters more

Use dynamic dispatch when rule selection changes at runtime or plugin-style extension is required.

.Dynamic dispatch engine: trait objects for runtime flexibility
[source,rust]
----
include::../src/ch06/risk.rs[tag=dyn_risk_engine]
----

Here, the engine stores `Box<dyn RiskCheck>`. Calls go through a vtable, which adds a small runtime indirection. In return, configuration can choose implementations without recompiling this engine layer.

Use this model when operator-configured policy changes are common. Avoid it when every nanosecond on a hot path matters and rule sets are fixed per deployment.

A common pattern is hybrid composition: generic engine in the core ingest path, dynamic engine in tooling or policy simulation commands. That keeps production hot paths predictable while preserving runtime experimentation outside the critical loop.

The primary action is comparison: run `generic_and_dyn_engines_agree_on_rejection` and confirm both engines reject the same order under the same state. Behavior parity matters more than microbenchmarks at this stage.

.Running the integration test for <<ch-traits-generics-for-risk,traits and generics for risk>>
[source,shell]
----
cargo test --test integration_ch06 generic_and_dyn_engines_agree_on_rejection -- --exact
----

If parity fails, stop and fix semantics before discussing performance. Dispatch strategy should never change decisions.

=== One decision, backed by measurement

Make dispatch choice with measured evidence from your environment, not generic advice. Use one repeatable fixture and capture:

1. Decision latency per order.
2. Throughput at fixed rule set.
3. Binary size impact for generic specialization.

Then decide explicitly:

1. If latency is dominant and rule set is stable, keep generic dispatch.
2. If policy agility is dominant and latency budget allows it, choose dynamic dispatch.

This chapter's outcome is not "generics are always better." The outcome is "the dispatch model is chosen by a known constraint."

=== Traits + generics at the boundary

In a larger platform, keep core processing generic and bind concrete risk policy at composition boundaries (main entrypoint, service wiring, or test harness). That gives you local flexibility without leaking policy decisions into every call site.

This boundary placement is the real design lever:

1. Bind early with generics for predictable hot-path cost.
2. Bind late with trait objects for runtime configurability.

Choose once per component and document it. Hidden mixed strategy is where confusion starts.

At the API edge, prefer constructor names that encode dispatch mode so call sites stay readable. Clear construction makes operational intent visible in code review.

[NOTE]
====
The strongest signal that your risk boundary is healthy is boring tests: clear accept cases, clear reject cases, and identical behavior across dispatch modes.
====

The immediate payoff is operational confidence. Orders that violate policy fail before they mutate state, and that guarantee is enforced by types, not convention.
