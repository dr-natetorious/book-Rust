== Add a pre-trade risk check the type system enforces

Chapter 5 gave you error paths that stay readable under corruption. That makes a new question unavoidable: where does risk validation sit so bad orders never mutate state? You need a boundary that is configurable, testable, and hard to bypass by accident.

=== Risk checks are gatekeepers, not reports

Start with a concrete order and run both chapter 6 tests.

[source,shell]
----
cargo test --test integration_ch06
----

In this chapter, a risk check is the final step before state mutation: position cap, notional cap, or both. The point is not finance sophistication. The point is enforcing preconditions with types so each caller cannot invent its own interpretation.

The first reader action is mechanical: implement one check and make sure `approve` fails with `RiskViolation::PositionLimit` when the attempted position crosses the cap.

=== Generics and monomorphization in the hot path

----

----

The friction is binary size versus speed. Monomorphization emits a concrete copy per type parameter, which is usually what you want in hot code and occasionally what you regret in large binaries.

The chapter test `generic_engine_accepts_within_limits` is your confidence anchor for the happy path.

[source,shell]

----

The dry observation for this chapter: the type system will enforce your risk boundary all day, and it will not care how persuasive your exception to policy sounds.
