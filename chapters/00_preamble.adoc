== Preamble: Before You Write a Line of Rust

=== The problem Rust was built to solve

The hard problems in software don't change. Shared mutable state. Ownership of heap-allocated memory. Undefined behavior at the boundary between your code and someone else's. Whatever language you've been working in, you've met at least one of these in production — and it was expensive.

Rust doesn't fix those problems by introducing a runtime. It doesn't fix them by adding a garbage collector. It fixes them by making the common unsafe patterns unrepresentable at compile time. The borrow checker is Rust's static analysis pass for ownership and references: it tracks who owns a value, who is allowed to read it, and when mutation is legal. It is not a restriction — it's a proof. When the program compiles, certain categories of bugs provably cannot exist. Not "unlikely." Not "caught by the test suite." Cannot exist.

If you're coming from C or C++, think of this as taking the aliasing and lifetime rules you normally carry around in your head and asking the compiler to enforce them mechanically. If you're coming from Go, Java, or Python, the mental shift is different: values are not all implicitly shareable references managed by a runtime. Rust makes ownership part of the type story, and that is why the language can remove entire bug classes without a garbage collector.

That's the thing the language was built to solve.

=== Who this book is for

This book is for engineers who already know how to program and want Rust taught in the context of real work rather than isolated language drills.

It assumes you understand what a heap allocation costs. It assumes you know why data races are catastrophic — either because you've debugged one in production, or because you've thought carefully enough about shared mutable state to know you'd rather not. It does not assume you've already read a Rust book. When the prose uses a Rust-specific idea such as ownership, borrowing, or traits, it needs to earn that idea on the page.

What it will do is put you in situations where Rust's ownership model is the only clean solution. You'll meet unfamiliar syntax early, but always in the middle of a concrete task. You'll feel the friction of the wrong approach before you understand the right one. That ordering is intentional. The compiler errors you'll hit in <<ch-parse-binary-feed,parse-binary-feed>> are the syllabus.

If you're brand new to programming, this is the wrong first book. If you're a senior engineer coming from C++, Go, Python, Java, or a similar language and you want to become fluent in Rust by building something that matters, this is the book.

=== The platform you're going to build

The project runs for twelve chapters. Every line of code you write in <<ch-zero-copy-message-handling,zero-copy handling>> is still running in xref:12_publish_crate_semver_api.adoc#ch-publish-crate-semver-api[crate publishing].

The project is a market data platform: a system that reads a binary feed of financial messages, maintains a live order book, applies pre-trade risk checks, and publishes snapshots to downstream consumers. By the end, it's concurrent, async, tested, and packaged as a crate.

If you have not worked on trading systems before, the only thing that matters here is pressure. A feed handler ingests structured bytes at high volume. The order book turns those bytes into live state. Downstream consumers need snapshots that are fast and correct. That combination is useful because it creates immediate reasons to care about ownership, layout, allocation, and concurrency.

=== Toolchain setup

Install `rustup` — the Rust toolchain installer — from `rustup.rs`. On macOS or Linux:

[source,shell]
----
curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh
----

On Windows, download and run the `rustup-init.exe` from the same address.

Once complete, the stable toolchain is available as `cargo`, `rustc`, and `rustup`. Confirm the installation:

[source,shell]
----
rustc --version
cargo --version
----

Install the three tools you'll use throughout the book:

[source,shell]
----
rustup component add clippy rustfmt
----

`clippy` is a linter that catches common Rust anti-patterns — mistakes the compiler permits but that signal misuse. `rustfmt` is an opinionated code formatter. Both are invoked through Cargo:

[source,shell]
----
cargo clippy
cargo fmt
----

For editor support, install `rust-analyzer`. The language server is available as a Cargo-managed component:

[source,shell]
----
rustup component add rust-analyzer
----

Point your editor at the binary (`~/.rustup/toolchains/stable-*/bin/rust-analyzer`) or install the VS Code extension directly — it manages the binary automatically. The single most useful feature: inferred type display on hover. When you're learning what the compiler sees, that feedback loop is faster than running `cargo check` manually.

That type display matters more in Rust than it does in most languages. A variable is not just "some string" or "some collection." The type often tells you whether the value is owned, borrowed, mutable, shared, fallible, or pinned to a lifetime relationship the compiler is tracking. Hover text is not a convenience feature here. It is part of how you learn to read the program the way Rust reads it.

You don't need to configure any of these. The defaults work.

=== How to read a compiler error

Rust compiler errors are famously good. Famous for a compiler — adjust expectations accordingly, but not too far down. They are genuinely better than what you may be used to.

Here's a representative one. Don't try to understand the Rust concept yet — just practice reading the error structure:

[source,text]
----
error[E0382]: borrow of moved value: `msg`
  --> src/ch01/parser.rs:47:20
   |
44 |     let msg = parse_add_order(&bytes)?;
   |         --- value moved here (inferred)
45 |     process(msg);
   |             --- value moved here
46 |
47 |     println!("{:?}", msg);  // <-- msg is gone
   |                      ^^^ value borrowed here after move
   |
   = note: move occurs because `msg` has type `AddOrderMessage`,
           which does not implement the `Copy` trait
----

Read it in this order:

. **The error code** — `E0382`. You can look up any error code with `rustc --explain E0382`. Do this whenever an error is unfamiliar.
. **The location** — file, line, column. Open it.
. **The annotated span** — the compiler marks every relevant line, not just the one that failed. Read the labels on each.
. **The note** — the final sentence usually tells you _why_ the rule exists, not just that it was violated.

The span annotations are where the information is. The message at the top is a summary. Read the annotations first.

This is worth slowing down for because Rust errors often explain a rule you have been applying informally for years. In Python you might see a runtime failure after the fact. In Java you may get a type mismatch and move on. In C++ you may get no warning at all and then spend an afternoon with a debugger. Rust tends to stop earlier and tell you which ownership or borrowing rule you crossed while the code is still small enough to fix in one pass.

You'll spend real time on compiler errors in the first three chapters. That time is the investment. By <<ch-error-design-under-corruption,error design under corruption>> the errors read as fast as print statements — they're telling you something precise that you've already internalized. The chapter still takes the same clock time to resolve. It just stops feeling like a fight.

Most build systems tell you something broke. The Rust compiler tells you what you were thinking when you broke it.

=== Your first Cargo project

The repository for this book is already a Cargo workspace. Clone it, change into the directory, and run the test suite:

[source,shell]
----
git clone https://github.com/your-org/book-rust.git
cd book-rust
cargo test
----

You should see output ending with:

[source,text]
----
Running test\integration_ch01.rs

running 3 tests
test parser_smoke::rejects_truncated_payload ... ok
test parser_smoke::rejects_unknown_message_type ... ok
test parser_smoke::parses_single_add_order_from_fixture ... ok

test result: ok. 3 passed; 0 failed
----

Three parser tests passing against a deterministic hex fixture. You didn't write the parser yet — <<ch-parse-binary-feed,parse-binary-feed>> will walk through it line by line. The toolchain works, the crate compiles, the test harness runs.

If `cargo test` fails: check that you're on Rust stable 1.94.1 (`rustc --version`), and that you have no local uncommitted changes.

=== Downloading the sample data

Every exercise in this book runs against real Nasdaq ITCH 5.0 binary data. Nasdaq publishes historical sample files at:

[source,text]
----
emi.nasdaq.com/ITCH/Nasdaq%20ITCH/
----

Download the January 30, 2020 file. That's the day the WHO declared COVID-19 a Public Health Emergency of International Concern. The feed was under elevated volatility, high message volume, and unusual cancel-to-execute ratios. It's the most interesting sample in the archive. The file is approximately 5.2 GB compressed.

If you're on a slower connection, the December 30, 2019 file is 3.3 GB and works for every exercise.

[source,shell]
----
# macOS / Linux
wget -P data/ "https://emi.nasdaq.com/ITCH/Nasdaq%20ITCH/01302020.NASDAQ_ITCH50.gz"

# or with curl
curl -L -o data/01302020.NASDAQ_ITCH50.gz \
  "https://emi.nasdaq.com/ITCH/Nasdaq%20ITCH/01302020.NASDAQ_ITCH50.gz"
----

Do not decompress it yet. xref:11_ffi_libz_safe_wrapper.adoc#ch-ffi-libz-safe-wrapper[FFI decompression] will handle that in Rust. For now, the file goes in `data/` at the root of the repository. The tests from <<ch-parse-binary-feed,parse-binary-feed>> through xref:10_async_fanout_backpressure.adoc#ch-async-fanout-backpressure[async fan-out] run against deterministic fixtures and don't require this file. When an exercise says "the sample file," it means this one.
