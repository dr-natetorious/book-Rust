== Share live risk state across the platform without copying it

<<ch-traits-generics-for-risk,Traits and generics for risk>> gave you enforceable risk decisions. That boundary only works if every component sees current position state. The question now is ownership topology: who owns live risk state when parser, book, risk, and reporting all need it?

A single owner model works until the second consumer arrives. Then teams usually add snapshots. Snapshotting feels safe and quickly becomes expensive: stale reads, copy overhead, and uncertainty about which snapshot made which decision.

This chapter replaces snapshot sprawl with explicit shared-state patterns. You will choose between borrowed views, single-thread interior mutability, and cross-thread synchronization based on access pattern instead of habit.

=== Three components, one state, conflicting timelines

The conflict is easiest to see on a busy window:

1. Parser emits an order.
2. Risk check needs current position now.
3. Book mutation updates position.
4. Reporting asks for a read at the same moment.

Those actions overlap. If ownership is exclusive and unshared, one component blocks or copies.

Start with the read-only view first. Lifetimes are easier when you understand the borrowing first.

`'a` is a relationship label, not a timer. It ties borrowed fields to a valid owner scope so the compiler can reject dangling access at compile time.

Read `&'a str` and `&'a f64` as: these references are valid as long as the owner behind `'a` remains valid. That is enough to model read views without allocating new copies.

If you are coming from C++: this is reference validity made explicit in signatures. If you are coming from Go: this is similar intent to sharing pointers, but aliasing/mutability constraints are enforced by the type checker.

=== The wrong design, caught at compile time

Try to compile this. Understand the error before moving forward.

.Attempting mutable access through Arc without interior mutability
[source,rust]
----
include::../src/ch07/arc_without_mutex_broken.rs[tag=arc_without_mutex_broken]
----

[listing]
----
error[E0596]: cannot borrow data in an `Arc` as mutable
  --> src/ch07/arc_without_mutex_broken.rs:10:5
	|
10 |     handle.positions.insert(symbol, entry + delta);
	|     ^^^^^^^^^^^^^^^^ cannot borrow as mutable
----

`Arc` shares ownership across threads, but it does not grant mutable access. The name matters: **Arc** is "Atomic Reference Counted," not "Atomic Reference Counted Mutable." If you want mutable access through an Arc, you need interior mutability: a Mutex or RwLock or RefCell that defers the mutability check to runtime.

[WARNING]
====
*Thread-safe shared state is not the default.* You must ask for it explicitly with `Arc<Mutex<T>>` or `Arc<RwLock<T>>`. If you forget, the compiler will refuse to compile the spawned task. You do not get silent data races.
====

This is a feature. The compiler is catching a bug before runtime.

Treat this error as a design checkpoint, not a syntax problem. If the compiler refuses mutation through `Arc`, it is telling you shared ownership exists but mutation policy is undefined. Add synchronization deliberately rather than patching around the error.

=== The ownership decision tree

Here is where lifetimes, Box, Rc, and Arc fit together:

.Ownership decision tree: choose by sharing scope and access pattern
[source,rust]
----

  A -->|Yes| C[Single-threaded access?]
  C -->|Yes| D["Use Rc<RefCell<T>><br/>reference counted<br/>runtime borrow checking"]
  C -->|No| E["Use Arc<Mutex<T>><br/>atomic counted<br/>sync-aware locks"]
----

This tree is your map. Follow it when you encounter shared state questions in your own code.

Keep one extra rule with the tree: pick the simplest option that satisfies current access needs, then upgrade only when requirements change. Starting with `Arc<Mutex<T>>` everywhere is convenient and often over-synchronizes single-thread workflows.

=== Single-threaded sharing: Rc and RefCell

When you have multiple references to the same data on one thread, use `Rc`. When you need mutable access through an `Rc`, wrap the mutable content in `RefCell` for runtime borrow checking.

.Single-threaded shared state with runtime borrow checking
[source,rust]
----
include::../src/ch07/shared.rs[tag=rc_refcell_state]
----

`Rc<RefCell<T>>` says: "I have multiple readers of the same data, all on this thread, and I need to mutate the data." The `Rc` handles reference counting (when the last `Rc` drops, the data is freed). The `RefCell` handles interior mutability (it allows mutable access without exposing `&mut`; the borrow check moves to runtime).

.Local mutation through RefCell borrow
[source,rust]
----
include::../src/ch07/shared.rs[tag=apply_fill_local]
----

If you try to hold two mutable borrows from RefCell simultaneously, `borrow_mut()` will panic at runtime. This is the runtime equivalent of the compile-time borrow check. You still cannot have conflicting borrows; Rust just defers the check to runtime in this case.

That panic behavior is useful in tests and dangerous in latency-critical production paths. Use it where single-thread ergonomics matter more than hard runtime guarantees. Avoid it in shared concurrent code where panic recovery is unacceptable.

=== Cross-thread sharing: Arc and Mutex

When you have multiple threads accessing the same data, use `Arc`. When you need mutable access, wrap the mutable content in `Mutex` for lock-based synchronization.

.Cross-thread shared state with lock-based synchronization
[source,rust]
----
include::../src/ch07/shared.rs[tag=arc_mutex_state]
----

`Arc<Mutex<T>>` says: "Multiple threads have references to the same data, and I need to mutate it safely." The `Arc` handles atomic reference counting (it uses atomic operations so multiple threads can safely update the reference count). The `Mutex` handles lock-based protection (it acquires a lock before granting mutable access; other threads wait for the lock to be released).

.Shared mutation through Mutex lock
[source,rust]
----
include::../src/ch07/shared.rs[tag=apply_fill_shared]
----

When you call `.lock()` on a `Mutex`, you get a "guard" that holds the lock until it is dropped. Only one thread can hold the guard at a time. Other threads wait. This guarantees that mutable access is exclusive, so no two threads can mutate the data simultaneously.

Lock scope is your performance lever. Keep guard lifetimes short and avoid doing expensive work while holding the lock. Apply minimal mutation, drop guard, continue processing. This discipline prevents lock contention from becoming your hidden throughput ceiling.

=== Understanding interior mutability

`RefCell` and `Mutex` both provide interior mutability: they allow mutation through a shared reference. The difference is when the conflict check happens. `RefCell` checks at runtime and panics if there is a conflict. `Mutex` checks with a lock: only one thread can acquire the lock and proceed.

The term is worth understanding because it explains why you need these types: normally in Rust, mutable access requires `&mut`, which the borrow checker enforces at compile time. Interior mutability allows `&T` to provide mutable behavior behind the type. The borrow checker trusts you (at compile time); `RefCell` or `Mutex` enforces the actual rule at runtime.

Use this mental model when choosing containers:

1. Compile-time exclusivity available: prefer plain `&mut`.
2. Single-thread shared mutation: `Rc<RefCell<T>>`.
3. Cross-thread shared mutation: `Arc<Mutex<T>>` or `Arc<RwLock<T>>` when read-heavy.

The goal is not to avoid interior mutability. The goal is to choose the smallest runtime mechanism that preserves correctness.

=== Choosing between Mutex and RwLock

In risk-state workflows, reads often dominate writes. That suggests `RwLock`, but measure before switching:

1. `Mutex` is simpler and often faster under moderate contention.
2. `RwLock` helps when read concurrency is high and writes are brief.
3. `RwLock` can regress if write frequency is higher than expected.

Start with `Mutex` in this chapter. Introduce `RwLock` only when profile data shows lock contention dominated by reads.

=== Summary

This chapter resolved the ownership topology problem that appears once multiple components need the same live data. You now have a concrete decision model for borrowed views, single-thread interior mutability, and cross-thread synchronization, and you have seen the compiler reject unsafe shortcuts before runtime can punish them. That is a major maturity point in Rust systems work: shared state is no longer improvised, it is designed.

The operational outcome is that lock boundaries and mutability costs are now visible choices. You can reason about guard scope, contention risk, and runtime borrow checks in terms of workload behavior, not just syntax rules. That makes code review sharper. The question shifts from "does this compile" to "does this ownership shape match expected access patterns under load," which is the question senior teams actually need answered.

The next step is to stress this design under read-heavy and write-heavy mixes so container choices remain evidence-driven. Keep deterministic state assertions across repeated runs to catch subtle concurrency regressions as architecture evolves. With state sharing now explicit and safe, the remaining pressure is raw throughput. <<ch-profile-and-optimize-hot-path,Hot-path profiling and optimization>> asks how much headroom the pipeline still has.
