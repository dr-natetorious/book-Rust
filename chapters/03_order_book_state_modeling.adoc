== Build an Order Book That Cannot Hold a Contradictory State

Your <<ch-zero-copy-message-handling,zero-copy parser>> can walk a market feed without allocating. It extracts individual messages from the stream with surgical precision. Useful, but incomplete: a parser that cannot maintain live state is just a well-behaved spectator.

The parsed messages need somewhere to land. An order book that tracks the current state of every live order. That is where Rust stops being a parser language and starts acting like a design language—because the state transitions are where correctness either lives or dies.

=== State models matter more than syntax

An order book is only a map from order reference to current state, but the real behavior lives in the transitions. Add creates a live order with initial shares. Execute reduces remaining shares. Cancel also reduces remaining shares, but for a different reason. Replace is simultaneous cancel-and-add. Once an order is closed—either through complete execution or explicit cancellation—further mutations are nonsense.

That is the domain context you need and all you need: orders move through stages, some transitions are invalid, and the model should make invalid transitions impossible to express.

The easiest bad model is a struct full of booleans. It compiles immediately and breaks slowly.

----

This struct compiles cleanly. It is also wrong—fundamentally, not just tediously. `live = true` and `canceled = true` can coexist. So can `executed = true` and `canceled = true`. `shares_executed` can exceed `initial_shares`. The type lets you represent states the business logic should never permit, which means every code path that reads this struct has to remember which boolean combinations are legal.

The burden falls on the caller. Every place that constructs or updates this struct is vulnerable to contradiction. Twice you miss checking a flag transition and the order book drifts into nonsense. By the third miss your tests don't catch it because they don't exercise that exact branch.

This is a familiar problem in any compiled language. In Java or Python, a cluster of booleans often starts as "simple state" and then grows contradictions. In C or C++, a struct with flags does the same thing. The weakness is not the language; it is the model. If the type can express nonsense, the rest of the codebase eventually will.

The solution is simpler than the problem: use an enum instead. Enums are not glorified constants. They are a way to say "this value is one of these shapes, and each shape carries different data." They are how you make contradictory states unrepresentable.

Now there is only one state at a time. `Open` and `Filled` and `Cancelled` are mutually exclusive because they are variant branches in the enum, not separate boolean fields. The impossible combinations are gone because there is nowhere to store them. An order is either open (which means you can execute or cancel it) or closed (filled or cancelled), and the type enforces that boundary at compile time.

This is where that principle lands: **make illegal state unrepresentable**. It is the first design principle in this book that matters beyond syntax.

If you know tagged unions from C, algebraic data types from functional languages, or sealed hierarchies from modern Java, Rust enums belong to that family. They are not glorified constants. They are a way to say "this value is one of these shapes, and each shape carries different data." That is why they are so good at modeling protocol messages and state transitions.

=== Let the event type do the dispatch

The feed handler already classified the binary wire records into message types. MessageView enum told the parser which shape each message held. The order book needs the same classification for state transitions.

Instead of one polyglot function that takes a message and figure out what to do with it, use an event type that says exactly what transition is happening. Add, Cancel, Execute, and Replace are not modes of one function; they are different operations with different consequences.

This is more than neatness. `BookEvent` forces every caller to name the operation it is performing. Add, Cancel, and Execute are not optional parameters. They are different variants with different payloads. Replace carries both old and new reference information because replacement is simultaneous cancel-and-add; a single variant captures that shape instead of asking the caller to construct two events and reason about their ordering.

That difference is easy to underestimate if you have spent years around APIs that accept one broad request object and validate combinations at runtime. Rust nudges the design earlier. Separate variants mean the type checker sees the operation boundary too, not just the business logic inside the method body. The shape of the enum variant is the first filter. The business logic inside the match arm is the second.

=== Exhaustive match is a logic checker, not just a statement

This method is the chapter's center of gravity. It is where invalid state transitions get named and rejected. Read the match arms carefully.

.Exhaustive match enforces valid transitions: every state-event pair is explicit
[source,rust]
----
include::../src/ch03/order_book.rs[tag=apply_event]
----

The `Add` arm rejects duplicates. The `Cancel` and `Execute` arms both funnel into a reduction path that checks the remaining shares before mutating anything. Most importantly, the closed-order case is explicit. If the order is already `Closed`, the transition fails immediately. There is no half-state where shares happened to change and the status update gets forgotten in some other code path.

`match` is doing two jobs here. Syntactically, it is a branch construct. Semantically, it is a completeness check. The compiler is asking: "Have you handled every shape this enum value can legally take?" If a new `OrderState` variant gets added, the compiler will refuse to compile until you handle it in every `match` statement that touches `OrderState`. If a new message type gets added to the protocol, the compiler will refuse to compile until you handle the corresponding `BookEvent` variant.

This is where exhaustive matching starts paying rent. Every legal combination of event and state gets handled. Every illegal one has to be named. The compiler is no longer checking syntax. It is checking whether your business logic forgot a branch. In many languages a `switch` or `if` ladder can quietly miss a case until production data wanders into it. Rust enums pair with `match` so the compiler can ask: have you handled every shape this value can take?

[NOTE]
====
*Exhaustive matching is not pedantry.* It is a compile-time check that every message type in the protocol is handled. If you try to add a new message without updating the order book logic, the compiler stops you. This is feature parity with runtime type systems, except the check happens at build time and costs zero runtime.
====

The friction you are feeling here is real. You have to enumerate every case before the code compiles. That feels verbose when you first see it. But that verbosity is the compiler asking you questions: "What happens when this message arrives while the order is already closed? What happens when you receive a replace for an order that doesn't exist?" You do not get to skip those questions. The type system answers them for you or refuses to compile.

Each layer does one job and hands the next layer something smaller and more precise.

That stepwise narrowing is worth naming because it is a reusable Rust pattern. Start with a broad representation close to the wire. Convert it into a domain event with stronger meaning. Apply that event to state with the narrowest API that still expresses the business rule. Each conversion throws away states the next layer should never have to think about.

It also means testing each layer independently: does the message parse correctly? Does the parsed message convert to an event? Does the event apply correctly? Each question is separate, so a bug in any layer gets caught where it actually is.

=== Test the complete path: parse, convert, apply

Run this chapter's tests to verify the full path works.

[source,shell]
----
cargo test --test integration_ch03
----

The happy-path test replays a deterministic stream with add, execute, and cancel messages. At the end there are zero open orders and two closed ones with explicit reasons. The failure test tries to execute more shares than remain and checks that the book rejects the transition instead of drifting into nonsense. Another test tries to cancel an order that doesn't exist and verifies the named rejection surfaces at the boundary.

That is the real win in this chapter. Not that the code compiles without errors. That the bad state has a name and gets stopped at the boundary. You can write a test that says "if this invalid transition reaches the order book, the book will reject it" and the type system guarantees you're not missing any cases.

The dry observation for this chapter: good state design lets the compiler ask "what could go wrong?" and then enforces that you answer every question explicitly.

=== Summary

This chapter moved the system from message processing to state correctness. The important win is not that events apply in sequence; it is that contradictory states became unrepresentable in the type model itself. Enums and exhaustive matching now do structural work that booleans and ad hoc conditionals cannot do reliably under growth. That means invalid transitions fail at the boundary with named reasons instead of silently drifting state over time.

You should feel a different kind of confidence at this point. Instead of trusting every caller to remember legal combinations, you can trust the state shape and match completeness checks to force explicit handling for each lifecycle branch. This changes review quality. Questions become specific: is this transition valid for this state variant, and does this error belong at this boundary? Those are design questions with deterministic answers, not style preferences.

To strengthen this chapter further, keep adding interleaved transition fixtures and ensure final state remains deterministic under replay. The more varied the sequence, the more value you get from type-driven constraints. Now that state integrity is enforceable, the next pressure is scale: <<ch-stream-full-day-memory-stable,streaming a full day>> asks whether these guarantees hold when input size is no longer polite.
