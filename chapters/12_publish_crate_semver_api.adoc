== Package the platform so another team can depend on it

<<ch-ffi-libz-safe-wrapper,FFI decompression>> closed the runtime pipeline. This chapter closes the product boundary.

An internal system can tolerate tribal knowledge. A published crate cannot. External users need a contract they can read, compile against, and upgrade safely.

This chapter turns your implementation into a durable API: constrained construction, controlled extension points, and explicit version-change semantics.

=== Learning objectives

By the end of this chapter, you should be able to:

1. Design a public API that prevents invalid construction at compile time.
2. Control extension points with sealed traits.
3. Classify version changes as compatible or breaking before release.
4. Run a release gate that protects downstream teams from accidental contract drift.

=== Design for the second version, not the first demo

The first version's API is often rough. You learned by building. The second version's API is what you ship to production. It should already assume that three more teams will need this code in three years and their upgrade success matters more than your development speed.

Use this filter for every public item: if you publish it, you own it for the lifetime of the major version.

Start with a builder that cannot construct an invalid client.

[source,rust]
----
include::../src/ch12/api.rs[tag=typestate_builder]
----

This is a pattern called typestate. Each builder method consumes one state and returns the next valid state. You cannot call methods out of order; the compiler prevents it. You cannot construct an invalid client; if you skip required fields, the compiler refuses to compile.

If typestate is new to your Rust toolkit, map it to interfaces with compile-time state transitions: each method consumes self in one state and returns self in the next state. If you cannot return the right state (you are missing required configuration), the method does not compile. There is no "configuration gets applied later" or "defaults kick in if you were not careful."

This is the opposite of the builder pattern you might know from Java or Python, where you can call methods in any order and hope the final object is valid. Rust's typestate makes invalid construction impossible at compile time. The caller does not have to remember the rules; the compiler enforces them.

Typestate pays off most when misconfiguration is expensive. Feed clients are a good fit because invalid startup should fail at compile time, not after connecting to production data.

=== Control extension points with sealed traits

Your downstream consumers care about predictable snapshot formats more than your domain internals. They write monitoring dashboards that parse your snapshots. They write audit code that depends on field names. They write integration tests against your API. If you change the snapshot format or expose a trait that someone implements, you break them.

Sealed traits let you expose behavior (anyone can call the method) without exposing extension points (no one outside your crate can implement the trait).

[source,rust]
----
include::../src/ch12/api.rs[tag=sealed_trait]
----

The technique is simple: define a private marker trait, make your public trait require it. Outside your crate, no one can implement your trait because they cannot implement your private trait. Inside your crate, you control all implementations.

This keeps extension policy intentional. If you later decide to open an extension point, you can do it deliberately with a new public trait and migration notes.

[WARNING]
====
*Public APIs are contracts.* Once a function is public and released, removing it or changing its signature is a breaking change. Code your API as if it will outlive your requirements. The highest-latency production bug is often a dependency upgrade that looked safe in release notes.
====

=== Make semver decisions explicit in code

Semantic versioning says:
- Major version (1.0 → 2.0): breaking changes
- Minor version (1.0 → 1.1): backwards-compatible additions
- Patch (1.0.0 → 1.0.1): bug fixes

Your code should make this decision explicit. When you change a public API, the type system should make it obvious whether it is breaking. When you update the version, your code should verify you made the right classification.

The key discipline is to classify changes before releasing, not after users report breakage.

The tests verify that:
1. A builder that correctly chains methods produces a valid client
2. Sealed trait implementations cannot be added outside your crate
3. Version transitions are classified correctly (1.0 → 2.0 is breaking; 1.0 → 1.1 is not)
4. API promises are kept: the snapshot format is precisely the same on every 1.x release

Add contract tests for serialized outputs that external systems parse. Snapshot stability is often the first accidental breaking change.

=== Release checklist for contract safety

Before publishing each release, run a fixed checklist:

1. Confirm no public signature changed unintentionally.
2. Confirm typestate transitions still prohibit invalid construction.
3. Confirm sealed traits remain sealed unless release notes say otherwise.
4. Confirm semver gate classification matches release version.
5. Confirm integration tests pass against previous minor-version fixtures.

This turns semver from documentation into an executable release process.

=== The contract language

Your API now has language:
- Typestate builders enforce correct construction
- Sealed traits prevent external implementations
- Structured errors let callers respond intelligently
- Version gates make breaking changes explicit
- Integration tests verify the contract works

When another team adopts your crate, they read the API and patterns and they understand the rules. Nothing is a surprise.

The dry observation for this chapter: good API design is not about elegance. It is about making misuse impossible and making correct use obvious.

[NOTE]
====
The best public API is boring to upgrade. If consumers are surprised, the contract was underspecified.
====

=== Completion criteria

Treat this chapter as complete only when all of the following are true:

1. Typestate builder prevents invalid construction sequences at compile time.
2. Sealed traits block external implementations unless explicitly opened.
3. Semver gate classifies major-version bumps as breaking and rejects malformed versions.
4. Release checklist is executed as part of the publish workflow, not ad hoc.

=== Summary

This chapter closed the loop between implementation and dependency stewardship. The platform is no longer just correct and fast in your repository; it is now shaped as a public contract other teams can consume without guessing hidden rules. Typestate construction, sealed extension points, and explicit semver classification give you a release surface that stays predictable as requirements evolve.

You should now be able to evaluate API changes through downstream impact rather than local convenience. That means identifying whether a change is compatible before publishing, proving behavior stability with integration tests, and treating release gates as engineering controls rather than paperwork. A good public API is not one that is clever in isolation; it is one that remains understandable and low-drama under repeated upgrades.
