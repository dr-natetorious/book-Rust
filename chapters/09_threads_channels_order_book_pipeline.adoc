== Chapter 9: Process the feed and update the book at the same time

Your chapter 8 exercise gave you a measured hot path and evidence that threads fit your workload. Now you split the monolithic processing into two independent components: one thread reads and parses, one thread maintains and updates the order book. They communicate through a channel.

The parser no longer blocks on book mutations. The order book no longer blocks on parsing frame headers. Both keep working at their natural pace. When one gets to a sync point—passing work to the other—the transfer happens through a channel guard. This is where concurrent Rust stops being abstract and starts being concrete.

=== Send and Sync show where data races are impossible

Before writing code, try to compile this deliberately broken version. Read the compiler error instead of pressing forward.

[source,rust]
----
include::../src/ch09/race_broken.rs[tag=race_broken]
----

[listing]
----
error[E0596]: cannot borrow data in an `Arc` as mutable
  --> src/ch09/race_broken.rs:14:9
	|
14 |         handle.insert(42, 1);
	|         ^^^^^^ cannot borrow as mutable
----

The compiler stopped you from writing a data race. Not "this might have a data race." Not "this could have a data race if the scheduler aligns badly." The compiler says: "This cannot compile because the type system proves it would have a data race."

[WARNING]
====
*Channels transfer ownership.* Once you send a value down a channel, only the receiving thread owns it. That is the locking mechanism. If you try to send the same owned value a second time, the compiler will refuse—because it is already owned by the first receiver.
====

That compiler stop is the chapter's first win. Shared ownership does not imply shared mutable access. You can have multiple readers; you cannot have one reader and one writer with overlapping accesses. The compiler verifies this statically.

=== The parser thread: read, parse, send

As message rates rise during volatile trading, parser work and order-book mutation compete for the same thread budget. Separating them means parsing can proceed while book logic catches up, even if the book is slower. You still process deterministic historical bytes, but now the pressure is pipeline coordination.

Start with the parser thread that owns the frame iterator and sends typed events through a channel.

The parser owns the iterator. It reads one frame, parses it into a `MessageView`, tries to convert that to a `BookEvent`, and sends the event down the channel. The channel sender is moved into the thread closure, so only this thread can send.

If parsing fails, the error travels through the channel too. The order book worker receives `Result<BookEvent, ParseError>` and decides what to do: fail fast or skip the bad record.

=== The book worker thread: receive, apply, report

Move order-book mutation behind a single receiving worker thread. This thread is the exclusive owner of the order book. No other thread can mutate it. No race conditions possible.

.A book worker thread: receives events and updates shared state
[source,rust]
----
include::../src/ch09/pipeline.rs[tag=book_thread]
----

The worker receives events from the channel. When an event arrives, it applies that event to the book. When the channel closes (the parser thread exits or panics), the worker loop exits too.

This design keeps one mutable owner of book state while still using multiple threads for throughput. The parser and book worker run concurrently. If the parser gets ahead, events queue in the channel (bounded by channel capacity). If the book gets ahead, it waits for the next event.

=== The discipline: one channel per responsibility

This scales to larger systems. One channel between parser and order book. One channel between book and risk engine. One channel between engine and reporting. Each channel carries one type of message. Each worker thread owns one piece of state.

The dry observation for this chapter: once you get the first channel working, you realize you can build arbitrarily complex pipelines without deadlock or data race. The type system guarantees it.
