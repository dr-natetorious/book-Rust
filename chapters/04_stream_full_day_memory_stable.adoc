== Chapter 4: Stream a full trading day without running out of memory

Your chapter 3 order book captures state transitions as types that make bad states impossible to express. It works perfectly on your fixture. That same code breaks silently when input stops being friendly.

The test fixtures you have been using are tiny: dozens of messages, a few kilobytes. But actual Nasdaq ITCH data for a full trading day compresses to 3.3—5.2 gigabytes. Decompress it and you get 10—20 gigabytes of raw binary records. That is an order book problem only if you load everything into memory first and then parse. It is a memory problem if your mental model is still "load all data, then process."

You need to flip that model. The parser from chapter 2 already consumes one record at a time. The missing part is a frame iterator that yields borrowed slices from a buffer without forcing you to hold the entire feed in memory at once. This is where Rust's explicit borrow semantics give you something you cannot easily get in other languages: you can iterate through gigabytes of data while holding only the current frame in memory.

=== The frame iterator: yielding slices without copying

The naive approach fails fast once data size grows. If you load the whole file, deserialize into owned Vec, walk the Vec:

[source,rust]
----
let data = std::fs::read("massive.itch")?;
let mut messages = Vec::new();
for chunk in data.chunks_fixed() {
  messages.push(OwnedMessage::parse(chunk)?);
}
// Now you have a 10GB Vec with 300M items
// Every one holding a copy of the parsed state
----

That works locally but breaks when your infrastructure team asks why you're running 64GB instances to process 3.3GB files.

This is the same tradeoff you have seen in other languages when you switch from materialized collections to streaming cursors: skip building the intermediate Vec. Instead, yield each item one at a time. Rust's version is explicit because the borrow ties each payload to the source buffer, so you do not accidentally keep old frames alive forever.

=== Iterators are lazy by default, and that is the point

The `Iterator` trait in Rust has one method: `next()`. Each call performs exactly one decode and returns immediately. No eagerness, no surprise allocations scheduled for later.

.Implementing Iterator for lazy frame decoding
[source,rust]
----
include::../src/ch04/stream.rs[tag=iterator_impl]
----

The friction you are feeling is real. Lazy evaluation requires mental discipline. With eager evaluation you can write `collect()` once and forget about how many items exist. With lazy evaluation you have to ask: "Who is consuming this iterator?" If no one calls `next()`, the iterator does nothing and produces no output and raises no error.

That is the core of lazy evaluation: nothing happens until you ask for the next item. No work, no allocation, no surprise. You pay for exactly what you consume.

Run one concrete action: call `next()` twice and inspect offsets. The first item starts at `0`, the second at `29` for the fixture used in tests. If those offsets drift, your memory profile might still look flat while your parser is silently skipping bytes. The test is your anchor.

[WARNING]
====
*Lazy iterators require intention.* If you forget to call `next()` or consume the iterator, no work happens and no error is raised. The iterator sits idle. Use assertions and allocator tracking in tests to catch silent misuse.
====

This pattern matters because it scales. One iterator reads frame boundaries, the next adapter turns frames into domain messages (`MessageView` from chapter 2), and downstream code only sees meaningful items. Each adapter compiles to simple loops with no hidden scheduler. You can map this directly to familiar ideas from Go channels or Java streams, but here each adapter costs zero allocation.

For file-backed inputs, move from borrowed slices to owned payloads while keeping the same iterator interface. The key is that the iterator owns the buffer, so each yielded frame is still a borrow tied to a single owner.

The file iterator owns the buffer. Each yielded frame is a slice borrowed from that single buffer. Once the iterator drops or advances, the old frame becomes invalid. That makes it impossible to build a Vec of frames by accident.

=== Verify zero allocations with cargo-asm

If `cargo-asm` is available in your environment, inspect the assembly for `FrameIter::next` before and after any refactor.

[source,shell]
----
cargo asm book_rust::ch04::stream::FrameIter::next
----

What you are looking for is absence of allocation calls. `call alloc::vec::Vec::extend_from_slice` should not appear in the hot path. `call core::slice::iter::next` is fine—that is the advancement logic. The confidence here is mechanical: if you see `malloc` or `Vec::push` in the assembly, your memory profile is not flat.

If `cargo-asm` is not available, use `cargo test --test integration_ch04` as your immediate confidence signal. The tests include allocator tracking. A failing allocation test means you have a leak waiting in your hot path.

=== Run the iterator pipeline

The dry observation for this chapter is simple: the bytes do not care how elegant your iterator chain looks. They only care whether you stopped allocating.

Run both the happy path and the failure tests:

The truncation test verifies that a malformed header returns an error instead of panicking and continuing with garbage. The file iterator test confirms that you can iterate across all frames without holding them in memory simultaneously. The performance test verifies that memory stays flat across thousands of frames.
