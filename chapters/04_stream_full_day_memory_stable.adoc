== Chapter 4: Stream a full trading day without running out of memory

You ended chapter 3 with an order book that survives the full fixture without panicking. That same code falls apart when input size stops being friendly. The next failure is not correctness. It is memory pressure from trying to stage more bytes than you need.

=== Why a 5GB file does not require 5GB of RAM

Start from the mistake on purpose: load everything, then parse. It works on tiny fixtures and quietly trains the wrong instinct. Run chapter 4 tests first so you have a baseline before changing flow.

[source,shell]
----
cargo test --test integration_ch04
----

The parser from chapter 2 already consumes one record at a time. The missing part is a frame iterator that yields borrowed slices and advances an offset.

[source,rust]
----
include::../src/ch04/stream.rs[tag=frame_iter]

This is the same tradeoff you have seen in other languages when you switch from materialized collections to streaming cursors. Rust's version is explicit because the borrow ties each payload to the source buffer, so you do not accidentally keep old frames alive forever.

Orders get added, cancelled, and replaced all day. On active sessions, cancels dominate. You care because the cancel path can be hot for hours, and a tiny allocation in that path becomes a large bill by market close.

=== Iterators are lazy, and that is the point

Now implement `Iterator` so `next()` performs exactly one frame decode and returns immediately.

.Implementing Iterator for lazy frame decoding
[source,rust]
----
include::../src/ch04/stream.rs[tag=iterator_impl]
----

Run one concrete action: call `next()` twice and inspect offsets. The first item starts at `0`, the second at `29` for the fixture used in tests. If those offsets drift, your memory profile might still look flat while your parser is silently skipping bytes.

[WARNING]
====
*Lazy iterators require discipline.* If you forget to call `next()` or consume the iterator, no work happens and no error is raised. The iterator is sitting idle. Use assertions and allocator tracking in tests to catch silent misuse.
====

The friction here is familiar: eager code usually looks simpler at first. Lazy code feels noisier because state moves into the iterator struct. The payoff is that you never hold more payload than the current frame.

This pattern matters because it scales: one iterator reads frame boundaries, the next layer turns frames into domain messages, and downstream code only sees meaningful items. === Verify zero-overhead intent with cargo-asm

If `cargo-asm` is available in your environment, inspect the assembly for `FrameIter::next` before and after any refactor.

[source,shell]
----
cargo asm book_rust::ch04::stream::FrameIter::next
----

If `cargo-asm` is not available, use `cargo test --test integration_ch04` as your immediate confidence signal and defer assembly inspection until chapter 8.

The dry observation for this chapter is simple: the bytes do not care how elegant your iterator chain looks. They only care whether you stopped allocating.
