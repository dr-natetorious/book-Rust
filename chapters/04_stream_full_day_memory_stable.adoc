== Stream a full trading day without running out of memory

Your <<ch-order-book-state-modeling,order-book model>> made contradictory state transitions impossible. That protected correctness once a message reached your state model. This chapter solves the part that happens before that: reading a full day of feed data without turning memory usage into the bottleneck.

The fixture flow hides the real constraint. A fixture with 40 records invites a comforting pattern: read all bytes, parse all messages, then apply them. Full-day Nasdaq ITCH files punish that pattern. The compressed file is usually 3.3-5.2 GB. After decompression, the raw stream is often 10+ GB. If the first step in your pipeline is "materialize everything," your machine is now a memory test harness instead of a feed processor.

Your parser already works record by record. The missing capability is delivery: producing one frame at a time from a shared buffer, then releasing it as soon as the next frame advances. This chapter is that pivot. You are not changing market logic. You are changing data movement so throughput and memory stay predictable under full-day replay.

=== The frame iterator: yielding slices without copying

The first version that usually appears is easy to read and expensive to run. Load the file, parse into owned records, then iterate the owned collection:

[source,rust]
----
let data = std::fs::read("massive.itch")?;
let mut messages = Vec::new();
for chunk in data.chunks_fixed() {
  messages.push(OwnedMessage::parse(chunk)?);
}
// Now you have a 10GB Vec with 300M items
// Every one holding a copy of the parsed state
----

That code is not wrong. It is just shaped for convenience instead of sustained replay. Memory grows with input size, allocator pressure climbs, and your deployment choice becomes "bigger instance" instead of "better pipeline." This is exactly the place where Rust gives you a mechanical alternative: parse views into borrowed slices, not owned copies, and advance a cursor.

The key decision in this iterator is ownership placement. The iterator owns the buffer and exposes each frame as a borrow tied to that owner. You can inspect the frame, parse it, and pass a parsed view downstream. You cannot stash old frames forever unless you copy them on purpose. The compiler forces the lifetime relationship, so memory discipline stops being convention and becomes type-checked behavior.

This mirrors streaming cursor designs from other ecosystems, but with stricter guarantees. In many runtimes, you have to trust a team convention that nobody retains references too long. Here retention boundaries are enforced by lifetime constraints in the API itself.

=== Iterators are lazy by default, and that is the point

The `Iterator` trait in Rust has one method: `next()`. Each call performs exactly one decode and returns immediately. No eagerness, no surprise allocations scheduled for later.

[source,rust]
----

----

The design pressure from laziness is operational clarity. You can always answer these two questions:

1. How much work happened?
2. Which call site caused it?

With eager materialization, one innocent `collect()` can hide a massive allocation step. With lazy iteration, work only happens when a consumer asks for another item.

That shifts how you test. For this chapter, assert cursor movement explicitly. Read frame 1, then frame 2, then assert the new offset. Those assertions catch parser drift early, before an end-to-end replay masks the bug with aggregate counts.

Lazy iteration is not a performance trick. It is the control surface that lets you stream a 10+ GB file through a bounded memory footprint.

[WARNING]
====
*Lazy iterators require intention.* If you forget to call `next()` or consume the iterator, no work happens and no error is raised. The iterator sits idle. Use assertions and allocator tracking in tests to catch silent misuse.
====

This composition pattern gives you a stable architecture under change:

1. Boundary reader handles offsets and lengths.
2. Parser adapter turns bytes into typed views.
3. Business logic consumes typed views only.

When an issue appears, diagnosis stays local. Boundary errors belong to stage 1, schema errors to stage 2, state errors to stage 3. That separation is worth as much as the memory savings because it keeps failures explainable.

For file-backed inputs, move from borrowed slices to owned payloads while keeping the same iterator interface. The key is that the iterator owns the buffer, so each yielded frame is still a borrow tied to a single owner.

=== Verify zero allocations with cargo-asm

If `cargo-asm` is available in your environment, inspect the assembly for `FrameIter::next` before and after any refactor.

[source,shell]
----
cargo asm book_rust::ch04::stream::FrameIter::next
----

Do not read this output as an assembly class. Read it as a contract check for the hot path.

You want to confirm absence of allocation-heavy calls inside `next`. Seeing slice and bounds operations is expected. Seeing `Vec::push`, `extend_from_slice`, or allocator calls indicates a regression.

This is one of the few places where low-level inspection gives immediate practical value. A single accidental copy in this path is multiplied by every frame in a full-day replay.

If `cargo-asm` is not available, use `cargo test --test integration_ch04` as your immediate confidence signal. The tests include allocator tracking. A failing allocation test means you have a leak waiting in your hot path.

=== Run the iterator pipeline

Now run the chapter tests as a pipeline health check.

Run both the happy path and the failure tests:

.Running the integration test for <<ch-stream-full-day-memory-stable,streaming a full day>>
[source,shell]
----
cargo test --test integration_ch04
----

Interpret the suite in three groups:

1. Boundary correctness: frame lengths and offsets move as expected.
2. Failure behavior: truncation and malformed records return typed errors.
3. Memory behavior: no allocation growth in steady-state iteration.

If group 1 fails, stop and fix parser boundaries first. If group 2 fails, your error handling is not preserving safety under bad input. If group 3 fails, your throughput tuning later in <<ch-profile-and-optimize-hot-path,hot-path profiling>> will be misleading because allocator churn is already distorting baseline performance.

=== Summary

This chapter changed the system's scaling behavior. You no longer need memory proportional to feed size just to make progress. Iterator boundaries, lazy pull execution, and frame-local processing now let you traverse long streams while keeping memory pressure predictable. That shift matters because it protects every later chapter from hidden preconditions like "works only on small fixtures" that collapse when real data arrives.

The meaningful learning outcome is that you can now prove memory behavior, not assume it. Frame offsets, truncation points, and allocation patterns are observable and testable, which means refactors can preserve scale properties with the same discipline used for correctness. When replay fails, you can tell whether the problem is framing, allocation regression, or downstream logic, instead of treating all failures as generic performance noise.

From here, continue hardening around hostile inputs and boundary cases. Add truncated fixtures, keep offset assertions stable, and compare short-run and long-run allocation behavior so surprises appear in tests first. With memory stability in place, the next dominant risk is trust in input quality. <<ch-error-design-under-corruption,Error design under corruption>> turns corruption from an implicit threat into an explicit control surface.
