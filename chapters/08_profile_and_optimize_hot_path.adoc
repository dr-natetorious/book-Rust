== Find and fix the allocation killing your throughput

<<ch-shared-state-lifetimes-pointers,Shared state and lifetimes>> gave you safe shared state. Safety is necessary and insufficient. Throughput now becomes the visible constraint.

At feed scale, tiny costs dominate. One extra allocation in a per-message path is not one allocation. It is hundreds of thousands per second. That cost leaks into latency variance, allocator contention, and inflated hardware requirements.

This chapter is about evidence-driven optimization: establish baseline, isolate hot path, make one change, verify outcome, keep or revert.

=== Learning objectives

By the end of this chapter, you should be able to:

1. Establish a repeatable baseline for throughput and allocations.
2. Isolate one hot path and prove a cost reduction with fixture-stable tests.
3. Validate optimization claims using generated artifacts (`cargo asm`) instead of intuition.
4. Choose threads or async based on workload shape, not framework preference.

=== Establish a baseline before you optimize anything

The first rule of optimization: measure before you touch anything. Write down the baseline numbers. Without them, you cannot prove your changes helped and cannot catch regressions later.

.A measurement harness: tracking allocations and latency on the hot path
[source,rust]
----
include::../src/ch08/hot_path.rs[tag=baseline_profile]
----

Run it against your deterministic fixture stream and capture three values: parsed messages, add-message count, and modeled allocations.

[source,shell]
----
cargo test --test integration_ch08 hot_path_smoke::baseline_profile_establishes_reference_point
----

The output tells you: "Parsed 100 messages, including 87 add orders, with 2610 allocations." Treat that as your baseline contract for this fixture.

Record baseline in source control notes, not memory. A baseline that lives only in terminal output gets lost and invites accidental regression acceptance.

[WARNING]
====
*Do not optimize based on intuition.* Measure first. The code path that feels slow is often not the bottleneck. The code paths you cannot see are usually the ones that surprise you.
====

=== Find the hot path with evidence, not instinct

In real feed windows, add-order traffic dominates. One avoidable allocation in that path becomes an allocation tax paid hundreds of thousands of times per second, so that is the path to optimize first.

Both implementations can pass correctness tests, so this is where teams regress silently. Keep at least one allocation-sensitive test in CI.

.The optimized variant: reusing buffers instead of allocating
[source,rust]
----
include::../src/ch08/hot_path.rs[tag=optimized_profile]
----

Run the optimized profile and compare modeled allocations first.

.Running the comparison
[source,shell]
----
cargo test --test integration_ch08 hot_path_smoke::optimized_profile_reduces_modeled_allocations -- --exact
----

The same fixture should show the core difference clearly: one path allocates per message, the other allocates once and reuses.

Keep interpretation strict:

1. Allocation count dropped and correctness unchanged: keep change.
2. Allocation count unchanged: revert and inspect assumptions.
3. Allocation count dropped but correctness changed: reject change.

=== Read generated behavior before claiming a speedup

Use assembly here as a contract check, not as an academic exercise.

Use `cargo asm` to inspect the function you changed:

[source,shell]
----
cargo asm book_rust::ch08::hot_path::baseline_profile
cargo asm book_rust::ch08::hot_path::optimized_profile
----

You are checking that repeat allocation calls left the steady-state loop. Look for `call alloc::vec::Vec::extend_from_slice` in the baseline; it should be gone or moved outside the loop in the optimized version.

.Assembly diff excerpt: allocation call removed from steady-state loop
[source,text]
----
baseline:
  ...
  callq core::slice::iter::next
  callq alloc::vec::Vec::extend_from_slice  <-- in the loop
  ...

optimized:
  ...
  callq core::slice::iter::next
  ...
----

(no Vec extend in the loop)

If that call disappears from the loop, the optimization did what you intended.

If assembly inspection is unavailable on your machine, pair allocation counters with latency percentile checks in a controlled fixture run. It is a weaker signal than assembly plus counters, but still better than intuition.

=== One change, one measurement discipline

Keep the discipline narrow: change one thing, rerun one measurement, record the delta. If two metrics moved, rerun with one more controlled edit so you can attribute cause.

Most optimization failures are attribution failures: too many changes at once and no reliable explanation for the gain.

A useful guardrail is "one hypothesis per commit." If a commit claims two unrelated performance wins, split it before merging.

=== Threads versus async: a workload decision, not a default

With a measured hot path, the concurrency question becomes workload fit, not preference.

.Workload characteristics: fixed vs. variable latency
[source,rust]
----
include::../src/ch08/hot_path.rs[tag=workload_model]
----

Feed parsing is bounded, CPU-heavy conveyor-belt work. Threads fit that shape.

Async fits fan-out: one producer, many consumers, variable completion times.

Threads and async are tools, not progression levels. Choosing threads here does not block async in xref:10_async_fanout_backpressure.adoc#ch-async-fanout-backpressure[async fan-out and backpressure].

[NOTE]
====
Optimization decisions should be reversible. Keep benchmarks, fixture size, and measurement command lines close to the code so future changes can revalidate assumptions quickly.
====

The bottleneck you can measure is the only bottleneck worth optimizing.

=== Completion criteria

Treat this chapter as complete only when all of the following are true:

1. Baseline and optimized runs are both captured for the same fixture.
2. Allocation deltas are explained in terms of one concrete code change.
3. Correctness tests still pass after optimization.
4. Your concurrency model decision is documented with measured evidence.
