=== Find the hot path with evidence, not instinct

In this feed, add-order traffic dominates busy windows and every avoidable allocation on that path compounds into latency under load. That is the only domain context you need for this chapter: cancel and execute logic matter, but the add-order parse path is where the allocation tax gets paid most often.

[WARNING]
====
*Do not optimize based on intuition.* Measure first. The code path that feels slow is often not the bottleneck. The code paths you cannot see are usually the ones that surprise you.
====\n\nThe friction here is practical: both versions parse the same data, both produce valid counts, and only one changes the cost profile. If you skip measurement, both implementations look equally correct in code review.

=== Read generated behavior before claiming a speedup

Use `cargo asm` to inspect the function you changed, then compare instruction shape between baseline and optimized variants.

[listing]
----
$ cargo asm book_rust::ch08::hot_path::optimized_profile
...
callq core::slice::iter::next
callq alloc::vec::Vec<u8>::extend_from_slice
...
----

The important move is not memorizing assembly syntax. You are checking that the change removed repeat allocation work from the steady-state loop.

The function you wrote quickly in an earlier chapter now decides whether your pipeline gets headroom or stalls quietly under traffic spikes. It waited until you had enough data to blame it.

=== One change, one measurement

Keep the discipline narrow: change one thing, rerun one measurement, record the delta. If two metrics moved, rerun with one more controlled edit.
