[[ch-async-fanout-backpressure]]
== Handle a live feed without blocking on slow consumers

<<ch-threads-channels-order-book-pipeline,Threaded pipeline>> split parser and book work into two threads with clear ownership transfer. That solved producer/consumer contention for one downstream path. This chapter addresses the next production shape: one producer, many consumers with different latency profiles.

Risk checks, audit logging, and reporting do not run at the same speed. If a slow consumer can block all others, your architecture is correct and operationally fragile.

This chapter introduces async fan-out with bounded queues so each consumer lane has isolated pressure and observable backpressure.

=== Learning objectives

By the end of this chapter, you should be able to:

1. Build bounded async fan-out lanes with explicit pressure behavior.
2. Measure and interpret backpressure per consumer lane.
3. Prevent mutex-across-await failures in spawned async tasks.
4. Define lane-level saturation policy (block, drop, or sample) from system requirements.

=== Futures are suspended work, not background threads

Async is not about doing thing in parallel. It is about suspending work when it would block, and resuming it when it becomes unblocked. This is different from threads, where the OS scheduler is what pauses and resumes.

Keep the model simple:

1. A future is deferred work.
2. `.await` is a yield point.
3. The runtime decides when to poll again.

You use async here because waiting behavior dominates, not because thread count is too low.

Start by building bounded channels for each consumer lane.

[source,rust]
----
include::../src/ch10/async_fanout.rs[tag=fanout_channels]
----

The key is `mpsc`: multiple producer, single consumer. Actually, the book is the single producer and each consumer lane is a single receiver. But Tokio's API calls it `mpsc` for historical reasons. Each channel has a capacity. When the channel fills up, senders wait. When a receiver drains the queue, senders can resume.

Capacity is a design decision, not a magic number. Small capacity surfaces consumer lag early and protects memory. Larger capacity smooths bursts and can hide chronic slow consumers. Start small in test and increase only with measured need.

If futures are new to your Rust mental model, map them to explicit state machines. A future is work that can be suspended and resumed. The Tokio runtime polls readiness: "Can this future make progress right now?" If yes, it runs. If no, it parks and checks again later. This is different from threads where the OS handles parking and unparking.

The practical takeaway: an `.await` inside a producer path is a potential throughput limiter. Keep awaited sections short and explicit so pressure points stay visible.

The runtime needs configuration. How many worker threads? What buffer sizes? What happens if a consumer task panics?

Feed plants care less about average consumer speed than about tail latency in one subscriber lane. A slow risk or logging consumer can force pressure on the producer queue even while other consumers are fast. That is what the bounded channels catch.

Treat fan-out lane metrics as first-class telemetry:

1. Queue depth over time.
2. Send wait duration.
3. Dropped or delayed event counts (if you add shedding later).

=== Observe backpressure instead of guessing at it

Backpressure is not magic. It is not automatic. It is observable. A bounded queue reaches capacity, the sender waits, and you record that the producer had to wait. That is backpressure.

Run the confidence tests and check that `backpressure_events` is non-zero when the slow consumer delay is enabled.

.Running the integration test for <<ch-async-fanout-backpressure,async fan-out and backpressure>>
[source,shell]
----
cargo test --test integration_ch10
----

The test runs twice: once with all consumers fast, once with one consumer intentionally slow. In the slow run, look at the backpressure count. That number is not a mistake. That is evidence that the bounded queue is doing its job: throttling the producer when consumers cannot keep up.

The hard idea here is operational: a bounded queue is not only a memory control, it is a measurement surface. Once you can count pressure events, you can decide whether to drop, shed, or slow ingestion deliberately. You have visibility into where the bottleneck actually is.

This is the point where architecture meets operations. Without pressure metrics, every slowdown looks like "the system is slow." With pressure metrics, you can name the lane and decide policy per lane.

Everything is concurrent and mostly calm until one subscriber blinks. Then the queue remembers exactly who blinked first.

=== Mutex across await: a async footgun

Try to compile this. Understand the error before moving forward.

.Holding a mutex guard across an await point: a bug the compiler catches
[source,rust]
----
include::../src/ch10/mutex_across_await_broken.rs[tag=mutex_across_await_broken]
----

[listing]
----
error: future cannot be sent between threads safely
  --> src/ch10/mutex_across_await_broken.rs:11:5
	|
11 |     tokio::spawn(async move {
	|     ^^^^^^^^^^^^ future created by async block is not `Send`
----

The error is cryptic at first read. What it is actually saying: "You are holding a synchronous `std::sync::Mutex` guard across an `.await` point. If this task is suspended while holding the guard, the scheduler might move the task to a different thread when it resumes. That violates the mutex invariants: a synchronous mutex cannot be held across thread boundaries."

[WARNING]
====
*Holding a synchronous mutex across an `.await` point is undefined behavior.* The compiler will reject the code at compile time. Use `tokio::sync::Mutex` in async contexts, not `std::sync::Mutex`.
====

The rule is direct: do not hold synchronous mutex guards across `.await` points in spawned tasks. Use async-aware primitives from Tokio or crossbeam.

Apply this guardrail in code review: if a lock guard variable is live at an `.await`, refactor immediately. Either narrow lock scope before `.await` or switch to async-aware synchronization.

=== The async/sync decision

You have async channels from Tokio for fan-out. You have bounded queues for backpressure visibility. You have error surfaces for monitoring. The pattern is: use async when you have many concurrent tasks with variable latency. Use threads and synchronous channels when you have a fixed set of workers doing CPU-bound work.

Your entire system now uses both: the parser and book worker are threads (<<ch-threads-channels-order-book-pipeline,threaded pipeline>>). The fan-out from book to risk/reporting/logger is async (this chapter). Threads for bounded, straightforward work. Async for fan-out, backpressure, and variable completion times.

The dry observation for this chapter: backpressure is not a bug. It is a measurement. You do not optimize it away; you make it visible and decide what to do about it.

[NOTE]
====
Backpressure policy belongs to product requirements, not individual call sites. Define whether each lane should block, drop, or sample when saturated, then implement that policy consistently.
====

=== Completion criteria

Treat this chapter as complete only when all of the following are true:

1. Fast and slow-consumer runs both execute against the same fixture.
2. `backpressure_events` is observed and explained for the slow-consumer case.
3. No synchronous mutex guard is held across `.await` in task code.
4. Lane saturation policy is documented and implemented consistently.

=== Summary

This chapter made fan-out behavior explicit under uneven consumer latency. Slow lanes no longer create mysterious global slowdown; they now produce measurable pressure signals and policy-visible consequences. That is the major outcome. Backpressure moved from an emergent symptom to a designed mechanism you can observe, tune, and explain.

You should now be able to read async lane behavior as operational telemetry, not just implementation detail. Queue depth, send wait time, and saturation events tell you where coordination is healthy and where it is masking capacity mismatch. Combined with the mutex-across-await guardrail, this gives you a practical checklist for writing async code that remains correct under scheduler movement and load spikes.

From here, deepen instrumentation before adding complexity. Keep lane metrics stable across fixture runs, encode saturation policy in tests when modes evolve, and treat async coordination changes as performance-sensitive architecture work rather than harmless refactors. With fan-out now pressure-aware and testable, the remaining manual gap is ingest setup. xref:11_ffi_libz_safe_wrapper.adoc#ch-ffi-libz-safe-wrapper[FFI decompression] moves that final boundary into code.
