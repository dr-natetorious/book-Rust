== Chapter 5: Handle every failure without crashing the platform

Your iterator pipeline from chapter 4 can run all day without blowing memory. The next problem is uglier: one corrupt record can still stop the whole replay or, worse, mutate state before failing. You need a failure model the caller can act on, not a crash and not a mystery.

=== What corrupt feed data looks like in practice

Use the deterministic corruption fixture and trigger the failure path first.

[source,shell]
----
cargo test --test integration_ch05 fail_fast_surfaces_the_offset_of_corruption -- --exact
----

[listing]
----
feed error at offset 29: unsupported message type: 90
^ offset points at the bad frame boundary
----

That line is the entire chapter in miniature: named failure, precise location, actionable next step.

[WARNING]
====
*Choosing between FailFast and SkipBadRecords is an operational decision, not a code smell.* The choice sticks to the architecture and gets made before event processing starts. There is no runtime flag or per-message override. Once you choose, the error surface reflects that choice.
====\n\nOn real feed days, most records are valid and a small fraction are broken by upstream tooling, truncation, or mixed capture boundaries. The platform decision is not whether corruption exists. It is whether you stop immediately or continue while preserving evidence.

`Result` plus `?` is not just syntax sugar. It forces a decision boundary at each operation that can fail: parse, convert, apply. In languages where exceptions can bubble from anywhere, this boundary is implicit. In Rust, the boundary is visible in the type and in the function signature.

=== Panic versus propagate, and how to test both choices

Library code in this project propagates corruption and book-transition failures. Panics remain for invariants that indicate programmer bugs, not bad input. This mirrors patterns you already know from production services: malformed request returns an error; impossible internal state aborts loudly.

The dry observation for this chapter: once you can name every failure, the scary part is no longer the crash. It is the list of failures that were always there.
