[[ch-error-design-under-corruption]]
== Handle every failure without crashing the platform

<<ch-stream-full-day-memory-stable,Streaming a full day>> gave you a memory-stable stream. The pipeline now handles a full-day file without preloading everything into RAM. That improvement exposes the next production constraint: input quality is not guaranteed.

One malformed frame in the middle of replay can do more damage than a crash. A crash is obvious. Silent partial application is not. If invalid bytes mutate state before failing, you get a wrong order book with no clear recovery point.

This chapter defines a failure boundary you can reason about: every bad record produces a typed error with enough detail to act. Rust's `Result` and `?` are the mechanics, but the real topic is policy design. Which failures stop replay? Which failures are rejected and logged so valid records keep flowing?

=== What corrupt feed data actually looks like

Corruption in market capture is usually boring and frequent, not dramatic:

1. Truncated transfer at the tail.
2. Bad message type byte from upstream conversion.
3. Length field mismatch that shifts frame alignment.

The practical consequence is always the same: your parser encounters bytes that do not map cleanly to the expected schema.

Use the deterministic corruption fixture first.

[source,shell]
----
cargo test --test integration_ch05 fail_fast_surfaces_the_offset_of_corruption -- --exact
----

The output shows:

[listing]
----
feed error at offset 29: unsupported message type: 90
^ offset points exactly at the bad frame boundary
----

That single line has the three properties you need in production:

1. Named failure (`unsupported message type`).
2. Precise location (`offset 29`).
3. Actionable boundary (you know exactly where replay diverged).

Without those three fields, incident response becomes guesswork. With them, you can alert, quarantine a capture, or replay from a safe checkpoint.

=== Make the error handling policy explicit

Do not hide policy in branch logic. Name it at the type level so callers choose behavior deliberately before processing begins.

.Defining the failure handling policy: FailFast or SkipBadRecords
[source,rust]
----
include::../src/ch05/errors.rs[tag=corruption_policy]
----

Each policy implies a different operational contract:

1. `FailFast`: stop at first corruption, return error immediately.
2. `SkipBadRecords`: keep valid flow moving, preserve rejection evidence.

Neither is universally correct. `FailFast` is safer for strict reconciliation pipelines where any corruption invalidates downstream results. `SkipBadRecords` is useful when partial continuity is preferred and downstream systems can tolerate explicit rejects.

[WARNING]
====
*Choosing between FailFast and SkipBadRecords is an operational decision, not a code smell.* The choice is made before event processing starts. There is no "I'll decide later" option. Once you choose the policy, the error surface reflects that architecture.
====

Treat this as a first-class API decision. If policy is implicit, two teams will assume different behavior and both will be surprised in production.

Make the selection criteria explicit in your runbook:

1. Choose `FailFast` when downstream consumers require contiguous, fully trusted replay windows.
2. Choose `SkipBadRecords` when continuity is more valuable than perfect completeness and rejected offsets are auditable.
3. Reject mixed semantics in one run. A replay that sometimes fails fast and sometimes skips records is impossible to reason about after the fact.

This is where platform ownership shows up. The parser does not decide policy. The caller does, once, up front.

=== Result and ? as design pressure

`Result<T, E>` puts error propagation in signatures instead of comments. That pressure is useful because it forces decision points at parse, decode, and apply boundaries.

.Applying the policy: Result and ? operator for error propagation
[source,rust]
----
include::../src/ch05/errors.rs[tag=replay_with_policy]
----

Read `?` as control-flow shorthand with intent: if this step fails, stop this path and return the typed failure now.

That leaves only two honest options:

1. Handle the error locally and continue under explicit policy.
2. Propagate the error and terminate this replay path.

What Rust removes is accidental swallowing. You cannot quietly forget a failing branch and still claim a total replay.

Another practical benefit is review clarity. When `Result` is threaded through the pipeline, code review can verify where failures are transformed, enriched, or propagated. Hidden catch-all behavior is much harder to hide in Rust than in exception-heavy codebases.

=== Design errors that callers can test and act on

Flat strings are easy to print and hard to automate. Structured errors are harder to design once and easier to operate forever.

.A structured error type: enums for testable failure modes
[source,rust]
----
include::../src/ch05/errors.rs[tag=processing_error]
----

Each variant should answer one operator question:

1. What failed?
2. Where did it fail?
3. Can replay continue under chosen policy?

This model also improves tests. You assert variant and fields, not output wording.

Add context fields only when they change an operator decision. Useful fields are offset, message type, and transition identifier. Expensive fields with low decision value should stay out of the core error variant and move into optional logging.

The success path should also preserve useful summary data for monitoring and retry logic.

.A report struct: success count, failure count, and failure details
[source,rust]
----
include::../src/ch05/errors.rs[tag=replay_report]
----

`ReplayReport` gives you clear post-run accounting:

1. `applied` for successful state transitions.
2. `rejected` with offsets and reasons.

That split matters in incidents. "Run failed" is not enough. You need to know if the failure happened before any valid application or after 900,000 valid transitions with three rejects.

It also matters for retries. If you store the last applied offset and the rejected offsets, you can replay deterministically from a known-good position after fixing a data source problem.

=== Build a deterministic failure test matrix

Before adding new error variants, add tests in a fixed matrix:

1. One corruption at first record.
2. One corruption in middle of stream.
3. One corruption at end of stream.
4. Multiple corruptions with valid records between them.

Run the matrix under both policies. The expected behavior should be obvious from the policy name alone. If you need a long explanation to justify expected output, the API surface is too ambiguous.

=== Run both failure modes and inspect the difference

.Running the integration tests for <<ch-error-design-under-corruption,error design under corruption>>
[source,shell]
----
cargo test --test integration_ch05 fail_fast_stops_on_first_bad_record -- --exact
cargo test --test integration_ch05 skip_bad_records_keeps_valid_records_moving -- --exact
----

Use these tests as policy acceptance checks:

1. `fail_fast`: first bad record stops processing and returns immediate typed failure.
2. `skip_bad_records`: bad record is recorded, valid records continue.

Capture both outputs. If counts differ from expectation, your branch behavior is no longer aligned with policy names.

Also assert ordering of rejections under `SkipBadRecords`. Stable ordering by offset is operationally important because it lets you compare runs and identify whether upstream capture quality is degrading over time.

=== Library code propagates, test code panics

Keep panic boundaries strict:

1. Library code returns typed errors.
2. Tests panic on impossible invariants.
3. CLI entry points may panic on unrecoverable startup failures.

This separation prevents a common failure mode where libraries panic because callers did not sanitize input. For a feed handler, malformed records are input reality, not exceptional logic bugs.

[NOTE]
====
When an error type is hard to test, it is usually hard to operate. Add structure first, then improve wording.
====

The practical payoff of this chapter is visibility. You now have a replay surface that can report exactly what failed and why, without sacrificing deterministic control flow.
