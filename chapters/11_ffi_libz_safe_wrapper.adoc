== Decompress the sample data without leaving Rust

<<ch-async-fanout-backpressure,Async fan-out and backpressure>> completed concurrent ingestion with visible pressure signals. One manual step remains outside your system boundary: decompression.

As long as decompression is manual, replay is not reproducible end to end. Different operators can produce different intermediate files, paths, or options and still claim they ran "the same job." That ambiguity is unacceptable once other teams depend on your crate.

This chapter pulls decompression into the codebase through an FFI boundary and introduces unsafe as a constrained tool for honoring foreign contracts.

=== Learning objectives

By the end of this chapter, you should be able to:

1. Define and enforce a safety contract around a C FFI boundary.
2. Isolate unsafe operations behind a safe Rust API.
3. Map foreign status codes into actionable Rust error variants.
4. Use deterministic tests and Miri to validate unsafe preconditions.

=== Start from the practical problem you already have

You have been staging decompressed data in test fixtures by hand. That works for learning but breaks for correctness. When you hand someone a 3.3GB compressed file and ask them to run your system against it, what happens? They uncompress it (sometimes wrong), they decompress it to the wrong path, they run the tool, and nothing matches your test environment.

Move the decompression boundary into your code.

The shift is operational as much as technical: inputs, transform, and output now live under one testable contract.

=== Unsafe is a permission set, not a style choice

`unsafe` is not an escape hatch from Rust's type system. It is a permission to do specific things the compiler cannot verify:
- Dereference raw pointers
- Call unsafe functions or FFI
- Access mutable statics
- Implement unsafe traits

Each permission comes with preconditions. If you violate the preconditions, you get undefined behavior. That is not Rust's fault; that is the C library's contract, which you must honor in code.

This chapter's domain context is minimal: sample files are distributed compressed for archive efficiency. Preprocessing outside your pipeline adds operational drift. You want to eliminate that step. That is the only justification you need.

Treat unsafe blocks like hazardous material handling: isolate, label, minimize, and inspect.

Try to compile this deliberately broken wrapper. Read the Miri report before proceeding.

----

----

[WARNING]
====
*Unsafe does not mean "no rules." It means "rules trusted to you."* Document the contract, state preconditions, and test violations. Miri will find many bugs faster than production users and makes much better feedback.
====

`unsafe` lets you perform operations the compiler cannot verify. Your job is to state and enforce the safety contract in code shape—not by comment, but in tests. Miri (an interpreter that detects undefined behavior) will catch violations faster than memory-safety tools will.

Good unsafe design has two characteristics:

1. Small unsafe region with obvious preconditions.
2. Safe outer API that makes invalid calls hard or impossible.

=== Wrap the C boundary in a safe function

Rust's strength is making unsafe boundaries small and auditable. Take the C library's raw interface (generic pointers, status codes returned as integers) and wrap it in Rust types that make misuse impossible.

.A safe Rust wrapper around the C decompression library
[source,rust]
----
include::../src/ch11/libz_wrapper.rs[tag=safe_decompress]
----

The wrapper owns three responsibilities: allocate output (caller provides size), call the foreign function, and map (potentially error) status codes to explicit Rust errors. The `unsafe` block is small: four lines. The ownership relationship is clear: the function allocates the output, calls the C function, and returns the owned Vec or an error. The caller cannot do anything wrong because the interface is too constrained.

The FFI contract is:
- Input: pointer to compressed data, input length
- Output: pointer to output buffer, output capacity, number of bytes written
- Status: integer status code
- Behavior: writes to output buffer, returns status

Document what the caller must ensure (input is valid UTF-8 if you care about encoding; output capacity is correct). Rust checks everything else.

Prefer documenting contracts as precondition bullets directly above the wrapper and mirroring each bullet with at least one test. Contract text without tests decays quickly.

=== Make the contract executable in tests

.Testing the FFI safety contract: input size, compressed payload, success condition
[source,rust]
----
include::../src/ch11/libz_wrapper.rs[tag=ffi_contract]
----

This test contract is deterministic: one byte declares payload length, remaining bytes carry data. That gives you a stable harness for success and corruption paths without network or timing variability. If decompression fails, you get a typed `LibzError`. If the output size is wrong, assertions catch it. If the input is actually corrupted (declared length differs from actual), the wrapper returns an error instead of guessing and continuing.

The test harness lets you verify safety without relying on fuzzing or stress testing. You can reason about specific error paths and verify the wrapper handles them correctly.

Add one more discipline here: verify no partially initialized output is exposed on error paths. Return errors before handing out buffers that appear valid but contain truncated bytes.

=== Run the integration tests

.Running the integration test for <<ch-ffi-libz-safe-wrapper,FFI decompression>>
[source,shell]
----
cargo test --test integration_ch11
----

The happy-path test decompresses a mock compressed payload and confirms the output matches expectations. The failure tests confirm that corruption is rejected, wrong sizes are caught, and invalid payload status codes return named errors.

Miri finds undefined behavior faster than production users and is dramatically less judgmental about the time of day.

Run Miri regularly while unsafe code is changing. Run it before releases even when unsafe code is unchanged.

=== The FFI boundary principle

This pattern holds at any FFI boundary:
1. Wrap the C API in a safe Rust function
2. Own the allocation and ownership transfer
3. Map C status codes to Rust errors
4. Test the contract systematically
5. Keep the `unsafe` block small and auditable

Add a sixth rule in this repo: keep raw FFI calls private to one module. Public API should expose only safe Rust types and error enums.

=== Regenerate bindings with bindgen when the C boundary changes

If the C surface changes, regenerate bindings instead of hand-editing signatures. `bindgen` keeps Rust declarations synchronized with the header contract and reduces drift between FFI declarations and linked library behavior.

[source,shell]
----
cargo install bindgen-cli
bindgen /usr/include/zlib.h -o src/ch11/bindings.rs
----

Treat generated bindings as build artifacts that must be reviewed but not manually curated line by line. Your safe wrapper remains the stable public surface; bindings are the raw boundary material.

The system you built now handles real compressed data. Everything from <<ch-parse-binary-feed,parsing>> through <<ch-async-fanout-backpressure,async fan-out>> still runs. The feed handler can now download, decompress, parse, maintain state, enforce checks, and fan-out to consumers—all without manual preprocessing steps.

The dry observation for this chapter: safe wrapper design moves the danger surface from "call C code" to "call this specific Rust function with this specific contract." The second one you can audit and test.

=== Completion criteria

Treat this chapter as complete only when all of the following are true:

1. Raw FFI calls remain private to one module.
2. Public callers interact only with safe Rust types and typed errors.
3. Corrupt input paths fail deterministically without exposing partial output.
4. Contract tests pass and include at least one UB-focused check under Miri workflow.
5. One binary path can download and decompress the sample file without a manual unzip step.

=== Summary

This chapter reframed unsafe code from "risky implementation detail" to "auditable boundary design." The decompression step now lives inside the system with explicit contracts, typed failures, and deterministic test coverage. That is the real value: not merely calling C from Rust, but constraining that call so downstream code cannot accidentally violate preconditions it does not even know exist.

You should now be able to reason about unsafe work in two layers. The inner layer is minimal and mechanical: pointer validity, length invariants, status-code handling. The outer layer is ergonomic and safe: stable Rust types, explicit errors, and predictable behavior under corruption. This split is what makes unsafe code maintainable in a multi-team repository. Without it, every FFI touchpoint becomes a latent incident source.

The next learning step is to harden contract drift detection. Add more corruption fixtures that fail for distinct reasons, and make Miri part of release discipline when unsafe-adjacent code changes. Keep rerunning integration tests whenever FFI signatures or buffer assumptions move, because this boundary fails expensively when left implicit. With decompression now integrated, the platform is functionally end to end. xref:12_publish_crate_semver_api.adoc#ch-publish-crate-semver-api[API publishing and semver] turns that working system into a durable dependency contract.
